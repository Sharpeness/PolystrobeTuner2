# Технический отчёт: Рефакторинг StrobTuner на стандарт C++23 и архитектура DSP-анализаторов (Solo & Polytune)

## Часть 1. Отчёт о проведённом рефакторинге на стандарт C++23

### 1.1. Цели и контекст миграции (C++17 → C++23)
Целью рефакторинга являлся перевод кодовой базы стробоскопического и полифонического тюнера **StrobTuner** (JUCE 8.0.4, форматы **VST3 / CLAP / Standalone ASIO**) со стандарта C++17 на **C++23** с соблюдением жёстких требований **Real-Time Audio Safety** и максимальной векторизации под компилятор **MSVC (Visual Studio / CLion, Windows x64)** с флагами `/O2 /Oi /Ot /arch:AVX2 /fp:fast /utf-8`.

---

### 1.2. Ключевые нововведения стандарта C++23, внедрённые в проект

#### 1. Безопасная обработка ошибок через `std::expected<T, E>` (взамен исключений и кодов возврата)
В реальном времени (аудиопоток) и при работе с системными ресурсами полностью исключены конструкции `try / catch / throw`. Вместо них применён шаблонный класс `std::expected` из `<expected>`:
- **`Source/dsp/TunerMath.h`**:
  Метод `TunerMath::frequencyToNote(...)` возвращает `std::expected<TunerResult, TunerError>` с типизированным перечислением ошибок `enum class TunerError : std::uint8_t { FrequencyOutOfRange, InvalidReferencePitch }`.
  Это позволяет на этапе компиляции гарантировать проверку валидности входной частоты (`20..4500 Гц`) и опорного строя `A4` (`400..480 Гц`) без накладных расходов на раскрутку стека (zero-cost error handling).
- **`Source/PluginProcessor.h` / `Source/PluginProcessor.cpp`**:
  Методы сериализации состояния автономного приложения `saveStandaloneStateFile()` и `loadStandaloneStateFile()` возвращают `std::expected<void, juce::String>`, явно сигнализируя об ошибках чтения/записи XML без генерации исключений.

#### 2. Безопасная передача буферов нулевой стоимости через `std::span<const T>`
Устаревшие пары аргументов `(const float* samples, int numSamples)` и возврат тяжёлых контейнеров `std::vector` заменены на невладеющие представления `std::span` из `<span>`:
- **`MpmPitchDetector::process(std::span<const float> samples)`** и **`PolyPitchDetector::process(std::span<const float> samples, bool monoHasStrongSingleLock)`**:
  Передача аудиоданных из `juce::AudioBuffer<float>` в оба DSP-детектора выполняется через единый дескриптор `std::span<const float>` без копирования памяти.
- **`TuningPresets::getPresets(bool isBass)`**:
  Возвращает `constexpr std::span<const TuningPreset>`, предоставляя мгновенный доступ к таблицам из 27 гитарных и 14 басовых пресетов прямо в сегменте константных данных (`.rdata`) без единой аллокации в куче.

#### 3. Вычисления на этапе компиляции (`constexpr` / `inline constexpr`) и `std::string_view`
- **`Source/dsp/TuningPresets.h`**:
  Все 27 гитарных и 14 басовых строёв (включая таблицы поправок **Peterson GTR Sweetener**, **Eddie Van Halen (EVH)**, **James Taylor / ACU**, **Buzz Feiten (BFE)** и Drop-строи) генерируются **на этапе компиляции** с помощью `constexpr`-функции `makeShifted(...)`.
- Строковые литералы имён пресетов, категорий и нот переведены с `juce::String` / `const char*` на `std::string_view` и `inline constexpr std::array<std::string_view, 12>`. Конвертация в `juce::String` выполняется только в UI-слое при отрисовке текста.
- Функции выборки активных струн `TuningPresets::getActiveStrings(...)`, расчёта поправок `getSweetenerOffsetForMidi(...)` и масок избранных пресетов `getDefaultFavoritesMask(...)` полностью объявлены как `[[nodiscard]] static constexpr ... noexcept`.

#### 4. Математические константы `<numbers>` и атрибуты оптимизации ветвлений
- Макросы `M_PI` и `juce::MathConstants` в DSP-ядре заменены на типизированные константы стандарта `<numbers>`: `std::numbers::pi_v<float>` и `std::numbers::sqrt2_v<float>`.
- Во всех критических методах проставлены атрибуты:
  - `[[nodiscard]]` — предотвращает случайное игнорирование возвращаемых значений расчётов частот, периодов и `std::expected`;
  - `[[unlikely]]` — подсказывает предсказателю ветвлений процессора (Branch Predictor), что граничные проверки на пустой буфер (`samples.empty()`) или выход за пределы диапазона не выполняются в штатном режиме;
  - `[[maybe_unused]]` — подавляет предупреждения компилятора при намеренном игнорировании статуса в деструкторе/конструкторе Standalone-режима.
- Применены **структурированные привязки (Structured Bindings)** при распаковке результата `TunerMath::frequencyToNote`:
  ```cpp
  if (const auto result = TunerMath::frequencyToNote(freq, a4, sweetenerOffset, capo); result.has_value())
  {
      const auto& [noteChar, sharpFlag, midiNote, octaveNum, centsVal, validFlag] = *result;
      // ...
  }
  ```

### 1.3. Соблюдение ограничений Real-Time Audio (`processBlock`) и оптимизация под MSVC AVX2

1. **Zero Heap Allocations (Нулевые аллокации памяти в аудиопотоке)**:
   - В классах `MpmPitchDetector`, `PolyPitchDetector`, `TunerMath` и `TuningPresets` отсутствуют `new`, `delete`, `malloc`, `std::vector` и `juce::String`.
   - Все рабочие буферы размещены статически внутри объектов процессора через `std::array` фиксированного размера (`alignas(32) std::array<float, 8192> fullBuffer`, `std::array<ResonatorChannel, 8> channels`, `std::array<float, 32> periodRing`).
2. **Wait-Free / Lock-Free синхронизация между Audio Thread и GUI Thread**:
   - Полностью отсутствуют `std::mutex`, `std::lock_guard`, `juce::CriticalSection`.
   - Передача параметров из UI в аудиопоток и телеметрии из аудиопотока в UI (частота, нота, центы, массив из 8 состояний струн `PolyTunerState`) построена исключительно на атомарных переменных `std::atomic<T>` с семантикой барьеров памяти `std::memory_order_relaxed` для данных и `std::memory_order_release` / `std::memory_order_acquire` для флагов готовности кадра (`isSignalActive`, `isPolyModeActive`).
3. **Авто-векторизация SIMD (AVX2 / FMA) в компиляторе MSVC**:
   - Рабочие массивы автокорреляции выровнены по границе 32 байта (`alignas(32)`), что позволяет инструкциям `vmovaps` / `vfmadd231ps` работать без штрафов за невыровненный доступ.
   - Указатели внутри горячих циклов помечены квалификатором `__restrict` (`const float* __restrict p1`), снимающим для оптимизатора MSVC предположение об алиасинге указателей.
   - Основной цикл расчёта NSDF развёрнут на 4 независимых аккумулятора (`acc0, acc1, acc2, acc3`) без единого внутреннего условного перехода (`if/else`), что обеспечивает 100% загрузку 256-битных YMM-регистров AVX2.
   - В начале `processBlock` установлен `juce::ScopedNoDenormals` (флаги процессора `FTZ` / `DAZ`), предотвращающий падение производительности CPU в 10–50 раз при затухании звука в рекурсивных БИХ-фильтрах (IIR resonators).

## Часть 2. Описание работы анализаторов сигнала (Solo и Polytune), физические проблемы гитарного сигнала и способы их решения

В плагине работают параллельно два специализированных анализатора:
1. **`MpmPitchDetector` (`Source/dsp/MpmPitchDetector.h`)** — высокоточный монофонический детектор основного тона для **Solo-режима** (стробоскопические дуги).
2. **`PolyPitchDetector` (`Source/dsp/PolyPitchDetector.h`)** — многоканальный банк резонаторов во временной области для **Полифонического режима (Polytune)** (одновременная индикация всех струн на матрице 23×5).

---

### 2.1. Монофонический анализатор (`MpmPitchDetector` — Solo Mode)

#### Принцип работы алгоритма
Анализатор построен на модифицированном двухскоростном методе Маклеода (**Dual-Rate McLeod Pitch Method — MPM**) с использованием нормализованной разностной функции квадратов (**NSDF — Normalized Square Difference Function**):
$$n'(\tau) = \frac{2 \sum_{i=0}^{W-1} x_i \, x_{i+\tau}}{\sum_{i=0}^{W-1} \left( x_i^2 + x_{i+\tau}^2 \right)}$$

Архитектура включает 4 этапа:
1. **Предварительная полосовая фильтрация и децимация**:
   Входной сигнал проходит через ФВЧ 1-го порядка (`35 Гц` для гитары / `14 Гц` для баса, удаляющий инфранизкий гул и постоянную составляющую) и перестраиваемый ФНЧ Баттерворта 2-го порядка (`520..1150 Гц` для гитары, `350..480 Гц` для баса в зависимости от ручки `Accuracy`). Затем сигнал записывается одновременно:
   - в полный кольцевой буфер `fullBuffer` на родной частоте дискретизации $f_s$ (`44.1..96 кГц`),
   - и с прореживанием в `decimationFactor` раз (`2x`, `4x` или `8x` до частоты $\approx 11..12\text{ кГц}$) в буфер `inputBuffer` размером `1024` отсчёта с шагом перекрытия `kHopSize = 256` (~21 мс).
2. **Грубый поиск периода по пикам NSDF на прореженной частоте**:
   В окне $W = 512$ вычисляется функция $n'(\tau) \in [-1, +1]$. Находятся все положительные локальные максимумы. В соответствии с критерием Маклеода выбирается **первый пик**, превышающий порог `cutoff = max(minClarity, highestVal * 0.85f)`.
3. **Двухскоростное уточнение пика на полной частоте дискретизации (`computeFineNsdfAt`)**:
   Найденная задержка $\tau_{\text{dec}}$ переводится в масштаб полной частоты дискретизации ($\tau_{\text{full}} = \tau_{\text{dec}} \cdot D$), после чего в окрестности $\pm D$ отсчётов по буферу `fullBuffer` вычисляется точная локальная NSDF на полной частоте $f_s$.
4. **Параболическая суб-сэмпловая интерполяция**:
   По трём точкам $(\tau_{\text{best}}-1, \tau_{\text{best}}, \tau_{\text{best}}+1)$ вершины пика строится парабола:
   $$\delta = \frac{\alpha - \gamma}{2(\alpha - 2\beta + \gamma)}, \quad T_{\text{exact}} = \tau_{\text{best}} + \delta, \quad f = \frac{f_s}{T_{\text{exact}}}$$
   Это даёт точность определения частоты **выше 0.1 цента**, необходимую для плавного вращения стробоскопических шкал.

#### Проблемы сигнала в Solo-режиме и их инженерные решения в коде
| Акустическая проблема | Физическая причина | Решение в `MpmPitchDetector.h` |
| :--- | :--- | :--- |
| **Проблема 1: «Пропущенный основной тон» (Missing Fundamental) и прыжки на октаву вверх** | У электрогитары (особенно на бриджевом звукоснимателе) амплитуда 2-й и 3-й гармоник часто в 2–3 раза превышает амплитуду основного тона $f_1$. Простой поиск глобального максимума автокорреляции ошибочно выбирает $\tau = T_0/2$ (октаву выше). | Использован критерий первого значимого пика Маклеода (`val >= highestVal * 0.85f`). Так как период основного тона $T_0$ объединяет энергию всех гармоник, пик на $\tau = T_0$ гарантированно превышает 85% от глобального максимума и выбирается первым, отсекая октавные гармоники. |
| **Проблема 2: Фантомная субгармоника при ударе по аккорду (~46.3 Гц, нота F#1/G1)** | При одновременном звучании струн 4, 3 и 2 их частоты соотносятся примерно как $3:4:5$, создавая акустическое биение с общим периодом $\approx 21.6\text{ мс}$ (`46.3 Гц`). Обычный MPM принимает это биение за одиночную басовую ноту и блокирует переход в Polytune. | Введена фильтрация по когерентности (`line 388`): в гитарном режиме частоты ниже `65 Гц` принимаются только при высокой чистоте периодичности одиночной струны (`highestVal >= 0.78f`). У аккордового биения `highestVal` составляет `0.48..0.62`, поэтому фантомная субгармоника надёжно отбрасывается. |
| **Проблема 3: Выброс частоты вверх (`+40..+50 центов`) в момент удара медиатором** | В первые 20–40 мс после удара медиатором в сигнале присутствует широкополосный щелчок и поперечный изгибный импульс струны. | При детекции атаки (`isAttack`) мгновенный сброс удержания частоты разрешён только при очень чистой периодичности (`highestVal >= 0.82f`, `line 394`). Если сигнал зашумлён щелчком медиатора, работает гистерезисный фильтр `candidateHits` (требующий до 3 последовательных подтверждений новой ноты). |
| **Проблема 4: Разделение логики Capo и поправок Sweetener** | Использование каподастра (`Capo`) меняет отображаемую ноту, но в полифоническом режиме пресет должен искать реальные открытые струны. | В `TunerMath::frequencyToNote` отклонение `cents` вычисляется строго от реального акустического MIDI-тона с вычетом `sweetenerCentsOffset`, а `capoSemitones` сдвигает только отображаемое имя ноты (`res.midiNote = nearestMidi - capoSemitones`). В `PolyPitchDetector` параметр `Capo` намеренно не передаётся. |

### 2.2. Полифонический анализатор (`PolyPitchDetector` — Polytune Mode)

#### Почему классический FFT (БПФ) не подходит для полифонического гитарного тюнера
На 6-й струне гитары (`E2 = 82.41 Гц`) или баса (`B0 = 30.87 Гц`) отклонение в **1 цент** составляет всего **0.047 Гц** (для `E2`) и **0.018 Гц** (для `B0`).
При частоте дискретизации $48\,000\text{ Гц}$ даже огромное окно БПФ в $65\,536$ отсчётов (задержка **1.36 секунды!**) имеет шаг между бинами $\Delta f = 48000 / 65536 = \mathbf{0.73\text{ Гц}}$ ($\approx 15\text{ центов}$ на 6-й струне!). Из-за спектрального просачивания соседних струн и гармоник фазовый вокодер БПФ даёт сильную нестабильность и огромную задержку.

#### Архитектура `PolyPitchDetector`: Банк резонаторов во временной области + суб-сэмпловый счётчик периодов
Вместо БПФ в `PolyPitchDetector` реализована параллельная многоканальная архитектура во временной области (по одному выделенному каналу `ResonatorChannel` на каждую струну пресета, до 8 струн):

1. **Анти-алиасинговая фильтрация и децимация до `~22..24 кГц`**:
   Входной сигнал фильтруется ФНЧ Баттерворта 2-го порядка со срезом `1800 Гц` и децимируется в 2 раза (при 44.1/48 кГц) или в 4 раза (при 88.2/96 кГц). Частота `24 кГц` обеспечивает высокое временное разрешение при низких затратах CPU.
2. **Индивидуальный 5-каскадный тракт изоляции каждой струны (`ResonatorChannel::processSample`)**:
   Каждый канал настроен на целевую частоту струны $f_{\text{target}}$ (с учётом пресета и поправки Sweetener) и включает:
   - **Ступень 0 (ФВЧ 1-го порядка на $0.80 \cdot f_{\text{target}}$)** — ослабляет фундаментальные колебания более толстых струн;
   - **Ступень 1 (Режекторный БИХ-фильтр Notch)** — точечно вырезает главную гармоническую помеху от соседних нижних струн;
   - **Ступень 2 (ФНЧ Баттерворта 2-го порядка на $1.22 \cdot f_{\text{target}}$)** — подавляет верхние гармоники самой струны и более тонких струн;
   - **Ступени 3–5 (Трёхкаскадный узкополосный резонатор 6-го порядка с полюсами на $\omega_0 = 2\pi f_{\text{target}} / f_{s,\text{dec}}$ и добротностью $Q = 15..18$)** — выделяет чистое синусоидальное колебание конкретной струны в окне захвата $\pm 55\text{ центов}$.
3. **Двухполупериодный суб-сэмпловый детектор пересечений нуля**:
   На выходе 3-го каскада резонатора (`y3`) фиксируются как восходящие (`prevSample < 0 && y3 >= 0`), так и нисходящие (`prevSample > 0 && y3 <= 0`) переходы через ноль с линейной суб-сэмпловой интерполяцией доли отсчёта (`frac`). Измеренные периоды, попадающие в физический допуск струны $\pm 55\text{ центов}$ (`minValidPeriod..maxValidPeriod`), записываются в кольцевой буфер `periodRing` на `32` полупериода.
4. **Статистическая фильтрация межквартильным усечённым средним (Interquartile Mean — IQR)**:
   Каждые `20 мс` (50 Гц) метод `computeStablePeriod()` сортирует накопленные периоды в `periodRing`, отбрасывает 25% минимальных и 25% максимальных выбросов и вычисляет среднее арифметическое центральных 50% значений ($q_1 \dots q_3$), а также межквартильный разброс `iqrSpreadCents` (меру фазовой когерентности сигнала).

### 2.3. Ключевые физические проблемы в Полифоническом режиме и их решения в коде

#### Проблема 1: Гармоническая коллизия 6-й и 5-й струн с 1-й и 2-й струнами
- **Физическая суть**:
  В стандартном гитарном строе (и во всех параллельно пониженных строях):
  - **3-я гармоника 6-й струны** ($3 \cdot f_6 = 3 \cdot 82.41 = 247.23\text{ Гц}$) точно совпадает с **основным тоном 2-й струны** ($f_2 = \text{B3} = 246.94\text{ Гц}$, разница менее 2 центов!).
  - **4-я гармоника 6-й струны** ($4 \cdot f_6 = 329.63\text{ Гц}$) и **3-я гармоника 5-й струны** ($3 \cdot f_5 = 3 \cdot 110.0 = 330.0\text{ Гц}$) точно совпадают с **основным тоном 1-й струны** ($f_1 = \text{E4} = 329.63\text{ Гц}$)!
  Поскольку массивная витая 6-я струна обладает гораздо большей энергией и временем затухания, чем тонкие необмоточные струны 1 и 2, любой фильтр, настроенный на $f_1$ и $f_2$, неизбежно захватывает 3-ю и 4-ю гармоники 6-й струны. В результате при перестройке 6-й струны синхронно ползут индикаторы 1-й и 2-й струн.
- **Решение в `PolyPitchDetector.h`**:
  1. **Перенос анализа 1-й и 2-й струн на их 2-ю гармонику (`harmOrder = 2`)**:
     При конфигурации каналов (`setTargetStrings`, строки 119–138) анализатор автоматически проверяет кратность частот струн пресета. Если $f_s / f_{\text{low}} \approx 3.0$ или $4.0$, канал переключается в режим `harmOrder = 2` и отслеживает **2-ю гармонику тонкой струны** ($2 \cdot f_2 = 466..494\text{ Гц}$ и $2 \cdot f_1 = 622..659\text{ Гц}$). На этих частотах мощные 3-я и 4-я гармоники басовых струн остаются на октаву ниже и подавляются каскадом фильтров более чем на `65 дБ`.
  2. **Подавление соседних гармоник режекторным фильтром (Notch)**:
     - Для 1-й струны (`2 * f1`) режекторный фильтр по умолчанию ставится на $3 \cdot f_2$ (3-ю гармонику 2-й струны).
     - Для 2-й струны (`2 * f2`) режекторный фильтр по умолчанию ставится на $3 \cdot f_3$, а когда 6-я струна звучит и расстроена более чем на `4.0 цента` (`std::abs(lowCh.smoothedCents) > 4.0f`), динамически перестраивается точно на частоту 6-й гармоники 6-й струны (`6.0f * lowActualHz`, $Q = 16.0$), полностью отсекая увод 2-й струны. При этом вблизи `0 центов` (`<= 4.0c`) динамический Notch принудительно отключается, чтобы не вносить фазовых искажений в полосу пропускания самой 2-й струны.

#### Проблема 2: Послеатаковый скачок натяжения и откат частоты («Pitch Rollback») на тонких струнах
- **Физическая суть**:
  В момент удара медиатором поперечное смещение струны $A$ увеличивает её мгновенное продольное натяжение ($\Delta T \propto A^2$). Из-за этого в первые `80..120 мс` после щипка частота струны физически завышена на `+4..+10 центов`, после чего за `150..300 мс` «откатывает» вниз к установившейся высоте тона.
  Кроме того, у тонких стальных струн (1 и 2) отношение пика атаки к сустейну (Crest Factor) очень велико: если запоминать пиковую энергию `peakEnergy` в момент удара медиатора (`t = 0`), то уже через `200 мс` огибающая падает в 3 раза, и пороговый гейт отключает обновление показаний до того, как струна завершила откат.
- **Решение в `PolyPitchDetector.h`**:
  1. **Увеличенный стартовый бланк атаки на тонких струнах (`channelBlankFrames = 6`, ~120 мс)**:
     При детекции общей (`isPickAttack`) или поканальной (`chAttack`) атаки на каналах с `harmOrder > 1` включается бланк длительностью `6` кадров (~120 мс) с полной очисткой кольцевого буфера периодов `flushPeriods()` и сбросом флагов пересечения нуля (`hasPosCross = false`, `hasNegCross = false`). Завышенные периоды первых 120 мс атаки вообще не попадают в буфер.
  2. **Фиксация `peakEnergy` на выходе из бланка атаки (а не на щелчке медиатора)**:
     Пока длится бланк атаки, `ch.peakEnergy = ch.rawRmsSmooth` и `ch.framesSincePeak = 0` непрерывно обновляются. В результате в момент окончания бланка (`t = 120 мс`) опорный уровень `peakEnergy` равен уже спавшему после щелчка уровню начала сустейна.
  3. **Двухрежимное окно слежения (`thinSustainValid`)**:
     - В течение `42` кадров после окончания бланка (до **~1.0 секунды** после удара) при `rawRmsSmooth >= peakEnergy * 0.22f` канал непрерывно обновляется, полностью отслеживая откат струны к истинной частоте.
     - Если же конкурирующие басовые струны (6-я и 5-я) не заглушают тонкую струну (`maxCollidingBassRms < ch.rawRmsSmooth * 1.5f`), ограничение по времени снимается полностью (`rawRmsSmooth >= peakEnergy * 0.08f`), что позволяет **подстраивать 1-ю и 2-ю струны колком на ходу** точно так же, как и толстые струны 3–6.

#### Проблема 3: Физическая негармоничность витых струн (Wound String Stiffness Inharmonicity)
- **Физическая суть**:
  Из-за изгибной жёсткости стального сердечника частота $n$-й гармоники струны выше кратной частоты основного тона:
  $$f_n = n \, f_1 \sqrt{1 + B \, n^2}$$
  В Solo-режиме широкополосный алгоритм MPM оценивает период по совокупности первых гармоник (чей энергетический центр тяжести смещён вверх), тогда как узкополосный резонатор Polytune на струнах 3–6 выделяет исключительно чистую первую гармонику $f_1$. Без поправки струны, идеально настроенные в `0.0 центов` в Solo-режиме, в полифоническом режиме выглядят заниженными на `1.6..3.5 цента`.
- **Решение в `PolyPitchDetector.h`**:
  Функция `inharmOffsetCents(baseFreqHz, harmOrder)` вводит калиброванную частотно-зависимую поправку для витых струн (`+3.45c` для 6-й струны и баса `< 90 Гц`, `+2.80c` для 5-й струны, `+2.95c` для 4-й струны, `+1.65c` для 3-й струны и `0.0c` для 2-й гармоники тонких струн 1–2), обеспечивая полное совпадение зелёной зоны между Solo и Polytune.

#### Проблема 4: Стабильное переключение режимов `Solo <-> Polytune` без ложных перескоков
- **Физическая суть**:
  При щипке одной толстой струны (например, 6-й) её мощные гармоники (2-я, 3-я, 4-я) возбуждают каналы 4-й, 2-й и 1-й струн. Если считать просто общее число активных каналов, тюнер будет ошибочно переключаться в полифонический режим при настройке одной 6-й струны.
- **Решение в `PolyPitchDetector.h`**:
  1. Формируется маска `isHarmonicOfLower[s]`: если частота струны $s$ кратна ($2\times, 3\times, 4\times$) любой звучащей нижележащей струне, такой канал помечается как потенциальная гармоника и **исключается** из подсчёта `nonHarmonicActiveCount`.
  2. Вход в Polytune разрешён только когда одновременно звучат как минимум `3` (для 6/7/8-струнной гитары) или `2` (для 4-струнного баса) **независимые негармонические** струны на протяжении `5` кадров подряд (`~100 мс`).
  3. Возврат в Solo-режим выполняется быстро (`soloOverrideFrames >= 6`, `~120 мс`), как только одна негармоническая струна начинает явно доминировать (`secondNonHarmonicRms < maxNonHarmonicRms * 0.18f`) и моно-детектор `MpmPitchDetector` подтверждает захват одиночного тона.

#### Проблема 5: Плавная визуальная индикация накала светодиодов в Polytune
- Вместо дискретного переключения столбцов матрицы 23×5 вычисляется непрерывная координата центра светового пятна по вертикали:
  $$\text{posY} = 2.0 - \frac{\text{cents}}{\text{polytuneTolerance}} \cdot 0.65$$
- Яркость каждого из 5 вертикальных рядов рассчитывается через косинусоидальное окно ($\cos^2$), где центральный ряд `row = 2` окрашен в изумрудно-зелёный цвет, а ряды `0, 1` (выше тона) и `3, 4` (ниже тона) — в красный. При приближении струны к точному строю красный светодиод плавно гаснет, а зелёный плавно разгорается, создавая физически достоверную имитацию движения накалом светодиодов, идентичную аппаратному TC Electronic PolyTune.

## Часть 3. На что обратить внимание при дальнейшем тестировании и эксплуатации

1. **Уровень входного сигнала (Input Gain / Hi-Z вход аудиоинтерфейса)**:
   - Порог шумового гейта полифонического детектора (`absFloor = 0.000040f`, ~`-88 dBFS`) настроен на чистый инструментальный вход (Hi-Z / DI). При использовании активных звукоснимателей или хай-гейн преампов перед тюнером рекомендуется ставить StrobTuner **первым плагином в цепи** (до компрессоров, грелок и усилителей), так как нелинейный клиппинг порождает интермодуляционные гармоники между струнами.
2. **Взаимосвязь настроек `In tune, cent`, `Polytune, cent` и `Accuracy`**:
   - Ручка **`Accuracy` (`10%..100%`)** одновременно регулирует полосу пропускания входного ФНЧ в Solo-режиме и скорость адаптивного фильтра сглаживания в обоих режимах. Для максимально быстрой черновой настройки всех струн оптимальны значения `70%..100%`; для финишной прецизионной отстройки мензуры — `30%..60%`.
   - Параметр **`Polytune, cent`** задаёт ширину центральной зелёной зоны в полифоническом режиме (рекомендуемый рабочий диапазон для быстрой проверки всех струн боем: `2.0..3.5 цента`).
3. **Особенности 7/8-струнных гитар и 5/6-струнных бас-гитар**:
   - На сверхнизких струнах (`F#1 = 46.25 Гц`, `B0 = 30.87 Гц`) физическое время установления колебания после удара медиатором составляет `140..180 мс`. Для наиболее точного считывания в полифоническом режиме рекомендуется извлекать аккорд равномерным движением медиатора средней силы (без резкого слэпа о лады), давая струнам свободно прозвучать `0.5..1.5 секунды`.
